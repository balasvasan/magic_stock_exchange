# Architecture

> 📊 **Visual reference**: [Master 10-day timeline](../assets/diagrams/00_master_overview.md) ([SVG](../assets/diagrams/00_master_overview.svg))

ARGUS is built as a four-layer Cloudera Data Platform stack, designed so that data flows up from the source systems through Bronze, Silver, and Gold tables on Iceberg, with the SDX governance plane cutting horizontally across all three lower layers.

![ARGUS architecture](../assets/architecture.svg)

## The four layers

**Layer 1 — Ingest (CDF)** is where the messy world outside the data platform meets the rigorous world inside. Apache NiFi flows handle the source-system plumbing: tapping the TARANG matching-engine multicast feed from inside the trading VLAN, pulling executed-trade events from the NIPATAN clearing system's Kafka mirror, consuming Debezium CDC events from the KAVACH KYC database, polling the SEBI Intermediary Portal SFTP endpoint for regulatory action notifications, mirroring the cross-exchange BBO vendor feed, and ingesting the news wire. NiFi validates record structure inline, attaches Atlas tag attributes (so PII-bearing flows are recognized at the moment they enter the platform), and routes failures to per-topic dead-letter queues. The nine production Kafka topics plus two DLQ topics — 126 partitions in total — are the shared event backbone consumed by all three streaming engines in Layer 2.

**Layer 2 — Process** is where the data engineering work happens, and where v1.2 introduces a deliberate split between three streaming engines that share the same Kafka backbone but specialize in different latency tiers. Spark Structured Streaming jobs (JOB-01 through JOB-04, on CDE) consume from Kafka and land Bronze tables in Iceberg with merge-on-read ORC files, schema-validated and partitioned by ingest date — Spark owns the canonical record. PyFlink CEP (JOB-10, on Cloudera Streaming Analytics) reads the same `orders.v1` and `trades.v1` topics and detects R-101 SPOOFING and R-102 LAYERING patterns with sub-second p99 latency, writing alerts to the new `realtime_alerts.v1` Kafka topic. SQL Stream Builder (JOB-11) hosts a declarative SQL streaming job for R-104 cross-product imbalance, deployable directly by surveillance analysts through the SSB UI. JOB-12 (Spark Streaming) closes the loop by reading `realtime_alerts.v1` and persisting it to `argus_${STUDENT_ID}_gold.realtime_alert_stream` — so both real-time engines feed a single, canonical, time-travellable record. Spark batch jobs (JOB-05 through JOB-08) build the Silver layer — SCD2 entity masters with fuzzy-match identity resolution that defeats the multi-broker manipulation pattern, cleaned and enriched order events, executed-trade records with both legs joined — and then the Gold layer of analytics-ready tables: per-second order-book reconstructions that answer "what did the book look like at instant T?", per-member temporal features that detect spoofing and layering signatures, cross-product features that detect Jane Street-style index manipulation. JOB-09 closes the loop by scoring each rule-fired alert with the ML model from Layer 3 and writing the score back to Iceberg every five minutes.

**Layer 3 — Serve** is where the platform becomes useful to humans. Cloudera Data Warehouse (Apache Impala) projects governed views over the Gold tables — three view families serving three audiences: surveillance analysts working the alert queue, the DPO and Compliance team working their audit responsibilities, the research team running aggregate analytics. Cloudera AI hosts the XGBoost alert risk-ranking model with MLflow tracking and registry; weekly retrains run from Airflow on CDE, and a manual approval gate moves the model from Staging to Production (regulators require humans in the loop on model promotions). Cloudera AI Inference hosts a locally-deployed open-weights LLM and a Milvus vector store containing the SEBI Master Circular, the PFUTP Regulations, and 200 historical exemplar STRs — together they generate Suspicious Transaction Report drafts in 8 seconds. Cloudera Data Visualization powers the surveillance ops dashboard tracking the team's KPIs.

**Layer 4 — Govern (SDX)** is the cross-cutting governance plane. Apache Atlas captures data lineage automatically as Spark and Impala write through the layers, and carries the six PRD-locked classification tags (`PII_HIGH_${STUDENT_ID}`, `PII_LOW_${STUDENT_ID}`, `FINANCIAL_SENSITIVE_${STUDENT_ID}`, `SURVEILLANCE_RESTRICTED_${STUDENT_ID}`, `DPDP_CONSENT_REQUIRED_${STUDENT_ID}`, `SEBI_AUDIT_TRAIL_${STUDENT_ID}`) on every column that has them. Apache Ranger enforces three policy families at query time: a row-level filter that removes consent-withdrawn investors from non-statutory queries (DPDP §6(4)), a column-mask family that redacts PAN/email/mobile for non-DPO roles, and a time-bound row-access policy that gives investigation leads full-PII visibility only during active cases. The DPDP §12 erasure workflow uses Iceberg time-travel — pre-action and post-action snapshot IDs captured in the `argus_${STUDENT_ID}_gold.consent_audit` table (which has `history.expire.enabled=false` so its history never expires) — to provide cryptographic evidence of erasure that survives a Data Protection Board audit.

| CDP service | Layer | Role in ARGUS |
|---|---|---|
| Apache NiFi (CDF) | 1 — Ingest | Streaming + batch ingestion, schema validation, DLQ routing, Atlas tag attribution |
| Apache Kafka | 1 — Ingest | Event backbone (9 production + 2 DLQ topics, 126 partitions) shared by all three streaming engines |
| Apache Spark (CDE) | 2 — Process | Bronze→Silver→Gold transforms, feature engineering, model scoring (JOB-01..09, JOB-12) |
| Apache Flink (CSA) | 2 — Process | Real-time CEP for R-101 SPOOFING + R-102 LAYERING (JOB-10, p99 < 800ms) |
| SQL Stream Builder (CSA) | 2 — Process | Analyst-deployed streaming SQL for R-104 cross-product imbalance (JOB-11) |
| Apache Iceberg | 2 — Process | Open table format with time-travel + schema evolution; MOR/ORC for Bronze, COW/Parquet for Silver/Gold |
| Apache Impala (CDW) | 3 — Serve | SQL serving for surveillance UI, BI queries, governed views |
| Cloudera AI (CML) | 3 — Serve | XGBoost training, Hyperopt hyperparameter search, MLflow tracking + registry |
| Cloudera AI Inference (CAII) | 3 — Serve | Locally-hosted LLM + Milvus vector store for STR narrative drafting |
| Cloudera Data Visualization | 3 — Serve | Surveillance ops dashboard with backlog + FP rate + time-to-disposition KPIs |
| Apache Atlas (SDX) | 4 — Govern | Classification tags, automatic lineage capture, audit trail |
| Apache Ranger (SDX) | 4 — Govern | Row/column policies, role-based access enforcement |
| Apache Airflow on CDE | Cross-cutting | Job orchestration, ML retraining schedule, DAG dependencies |

## Design decisions and their why

**Three streaming engines, one Kafka backbone.** ARGUS doesn't pick between batch and streaming, and it doesn't pick between Spark, Flink, and SSB. It runs all three on shared Kafka topics, each specialized for a latency tier the others can't serve well. Spark Structured Streaming owns canonical persistence (10-second triggers into Iceberg) — it's what feeds ML training and what regulators audit, and 10-second latency is fine for that role. PyFlink CEP owns sub-second pattern detection (R-101 SPOOFING and R-102 LAYERING in JOB-10, p99 < 800 ms) — fast enough that a surveillance analyst can intervene while a manipulation episode is still in progress, not after close. SSB SQL owns analyst-driven streaming (R-104 cross-product imbalance in JOB-11, ~30s window latency) — surveillance analysts write and deploy the pattern themselves through the SSB UI, with no engineering bottleneck. The same source events feed all three; the same `event_id` from a planted spoofing case lands in Bronze (canonical), `realtime_alerts.v1` (Flink, sub-second), and `gold.alert_candidates` (Spark batch, ~30 min) — and Lab 1.5's three-engine cross-check makes that explicit. The architectural lesson students take away: batch vs streaming is a false dichotomy; the right answer is a shared event log with multiple specialized consumers.

**Streaming-by-default in Bronze, batch-by-exception.** Five of the six Bronze tables are populated by Spark Structured Streaming jobs reading from Kafka. The sixth — `argus_${STUDENT_ID}_bronze.legacy_alerts` — is loaded once per day by a batch job because it's the SMRITI nightly export from the legacy vendor platform, and there's no value in pretending a nightly batch is real-time. The contrast is pedagogical: students see when streaming is the right answer (live order events) and when batch is correct (end-of-day historical labels), instead of dogmatically using Kafka for everything.

**Iceberg with MOR for Bronze, COW for Silver/Gold.** Bronze takes continuous appends and benefits from merge-on-read for late-arriving corrections without rewriting whole files; ORC compresses well on the high-volume order events. Silver and Gold are read-heavy analytic tables, so copy-on-write Parquet is faster on scans even if writes are more expensive. The `argus_${STUDENT_ID}_gold.consent_audit` table additionally has `history.expire.enabled=false` so DPDP audit history never expires — that property is what makes CP-19 (the COMPLIANCE GATE) provable.

**Single-tenant per student, multi-tenant per cluster.** Every student's S3 bucket name embeds their `STUDENT_ID` (e.g. `argus-sxx21-mum`), so the same CDP cluster serves an entire cohort without cross-student data collisions. The Kafka topics are shared across the cohort; the Spark jobs filter by `STUDENT_ID` in the checkpoint paths so each student's job state is isolated.

**Locally-hosted LLM for the GenAI module.** Personal data of Indian data principals cannot leave India under DPDP §16, and SEBI's separate market-data localization expectations don't help either. So the Module 6 RAG pipeline calls a Cloudera AI Inference endpoint hosting Llama 3.1 70B or Mistral Large on a GPU pool inside the customer's environment — never an external API. The choice is forced by regulation, not preference.

**Manual model promotion gates.** Every transition from MLflow Model Registry's Staging stage to Production is a clicked button in the MLflow UI, never an automated webhook. SEBI's draft AI/ML guidance for surveillance systems requires a documented human approval for every model deployment; the manual gate is what makes ARGUS defensible if challenged. The compliance evidence trail includes the description text the operator types into the dialog, so "Approved by [name], date [today], CP-13 metrics passed" becomes part of the inspection record.
